## 1. ガイドから抜き出した用語

### JWT（JSON Web Token）

- **JWT** は、「誰であるか」「何をしてよいか」を安全に運ぶためのトークン。
- 規格: RFC 7519。形式: JSON を Base64 風にエンコードした文字列。主な用途: ログイン後の認証・認可（API アクセス権の証明）。

### トークン

- **トークン** = 権利や状態を表す、短いデータの切れはし。
- 例: 遊園地の腕輪、投票用紙、乗車券。IT では「認証済みである」ことを示す文字列。サーバーは「このトークンが正しければOK」と判断する。

### RFC 7519

- **RFC** = Request for Comments。インターネットの技術仕様をまとめた文書。
- **RFC 7519** = JWT の仕様。トークンの構造（ヘッダー・ペイロード・署名）、クレーム名（`sub`, `exp` など）、エンコードのルールを定義。

### Base64 / Base64URL

- **Base64**: バイナリデータを「英数字と + / =」だけのテキストに変換する方式。暗号化ではなくエンコード（可逆変換）なので誰でもデコードして読める。
- **Base64URL**: Base64 とほぼ同じだが、`+`→`-`、`/`→`_` に置き換え、`=` を省略することがある。JWT のヘッダー・ペイロード・署名はすべて Base64URL でエンコードされた文字列。

### 共有秘密と秘密鍵の違い

| 用語                   | 意味                                          | 使う場面                                      |
| -------------------- | ------------------------------------------- | ----------------------------------------- |
| **共有秘密（共通鍵）**        | 1本の鍵を署名する人と検証する人で共有。同じ鍵で署名も検証も行う（例: HS256）。 | サーバーが1台、または鍵を安全に共有できる相手だけが検証するとき。         |
| **秘密鍵（Private Key）** | 公開鍵とペアのうち、自分だけが持つ方。署名は秘密鍵、検証は公開鍵（例: RS256）。 | 署名は1か所（認証サーバー）だけで、検証は多くのAPIが「公開鍵だけ」で行うとき。 |

### ヘッダー（Header）

- トークンの種類（JWT）と署名アルゴリズム（HS256, RS256 など）を宣言。JSON を Base64URL したものがヘッダー部分。

### ペイロード（Payload）

- 中身のデータ（誰のトークンか、有効期限、権限など）。JSON を Base64URL したもの。暗号化されていないので、パスワードなどを入れない。

### 署名（Signature）

- 「このヘッダーとペイロードの組み合わせは、秘密を知っている人だけが作れる」ことを証明する部分。「ヘッダー＋ペイロード」を秘密鍵とアルゴリズムで署名した結果を Base64URL したもの。改ざん検知の要。

### Bearer（ガイド上の説明）

- **Bearer** = 「このトークンを持っている者が権利者である」という認証方式の名前（Bearer スキーム）。`Authorization: Bearer <トークン>` の形で使う。

### SECRET 漏洩

- SECRET（共有秘密）や秘密鍵が漏れると、攻撃者は正しい署名を計算でき、好きな権限で有効な JWT を発行できる。改ざん検知では防げない。

### ステートレス

- **ステートレス** = サーバーが「今どのユーザーがログインしているか」などの**状態を保持しない**こと。JWT はトークン自体に必要な情報（誰か・期限など）を入れておくため、サーバーは受け取ったトークンを検証するだけでよく、セッションを保存しなくてよい。その分、サーバーを増やしても状態の同期が不要でスケールしやすい。

### 認証・認可

- **認証（Authentication）** = 「この人は誰か」を確認すること（ログインして本人だと確認する）。
- **認可（Authorization）** = 「この人にこの操作を許可するか」を決めること（例: 管理者だけがユーザー一覧を見られる）。JWT の `role` やスコープは認可の判断に使われる。

### Authorization（HTTP ヘッダー）

- **Authorization** = HTTP ヘッダーの名前で、「自分がこういう権限でアクセスしている」と示すために使う。JWT の場合は `Authorization: Bearer <トークン>` の形で、クライアントがトークンを送る。

### クレーム（claim）

- **クレーム** = ペイロードに入れる「主張・申し立て」のひとつひとつ。例: `sub`（主体＝ユーザーID）、`exp`（有効期限）、`role`（役割）。JWT の仕様で名前が決まっているもの（登録クレーム）と、アプリが自由に決めるもの（プライベートクレーム）がある。

### アルゴリズム混乱攻撃

- **アルゴリズム混乱攻撃** = 本来 RS256（公開鍵で検証）を使っているのに、攻撃者がヘッダーの `alg` を `HS256` に変え、**公開鍵を HMAC の秘密鍵として**使って署名し直す攻撃。検証側が「ヘッダーの alg を信じて検証する」実装だと、公開鍵で検証するため偽造トークンが通ってしまう。対策は検証時にアルゴリズムを固定（例: RS256 のみ受け付ける）こと。

### 攻撃例: ペイロード改ざんと署名検証での拒否（手順）

「ペイロードだけ `role: admin` に書き換えたい」という攻撃では、署名を秘密なしに再計算できないため、**元の署名のまま**「ヘッダー.改ざんペイロード.元の署名」を送ると、サーバーが再計算した署名と一致せず **401 Invalid token** で拒否される。手順の例は以下（ガイドの Node サーバーが動いている前提）。

1. トークンを `.` で分割: `HEADER`, `PAYLOAD`, `SIGNATURE`
2. ペイロードを Base64URL デコードして中身を確認（用語集「Base64」のデコード手順参照）
3. 改ざんした JSON を Base64URL エンコードして `NEW_PAYLOAD` を作る
4. `TAMPERED_TOKEN="${HEADER}.${NEW_PAYLOAD}.${SIGNATURE}"` で改ざんトークンを組み立てる（署名はそのまま）
5. `curl -H "Authorization: Bearer $TAMPERED_TOKEN" http://localhost:3000/api/me` で送る → 401 になる

Base64URL の扱い（`tr '_-' '/+'` やパディング `=` の補い方）は用語集「Base64」の手順を参照。

## 2. HS256・RS256 の「HS」「RS」「256」とは

アルゴリズム名は **「署名のやり方」＋「使うハッシュ」** で決まります。

### 256 の意味

- **256** = **SHA-256** を指します。
- SHA-256 は「入力から 256 ビット（32 バイト）のハッシュ値を出す」ハッシュ関数の名前です。JWT では「どのハッシュ関数で署名するか」を表す番号として使われています。

### HS の意味（HS256）

- **HS** = **HMAC with SHA-256** の略です。
- **H** = HMAC（Hash-based Message Authentication Code）。「秘密鍵とメッセージを組み合わせてハッシュし、改ざん検知・送信元の証明に使う」方式です。
- **S** = SHA-256 の S（SHA の S）。「HMAC の計算に SHA-256 を使う」という意味です。
- まとめ: **HS256 = 秘密鍵 1 本で、SHA-256 を使った HMAC で署名する方式**（対称鍵）。

### RS の意味（RS256）

- **RS** = **RSA Signature with SHA-256** の略です。
- **R** = RSA（公開鍵暗号の一種。署名・検証に使うアルゴリズム名）。
- **S** = SHA-256 の S。RSA で署名するときに「まずメッセージを SHA-256 でハッシュしてから、そのハッシュ値を秘密鍵で署名する」という意味です。
- まとめ: **RS256 = RSA と SHA-256 を組み合わせた署名方式**（非対称鍵。秘密鍵で署名、公開鍵で検証）。

### 一覧

| 名前        | 略の意味                       | 鍵の種類             |
| --------- | -------------------------- | ---------------- |
| **HS256** | **H**MAC + **S**HA-**256** | 共有秘密 1 本（対称鍵）    |
| **RS256** | **R**SA + **S**HA-**256**  | 秘密鍵・公開鍵のペア（非対称鍵） |

## 3. Bearer の日本語訳と名前の理由

### 日本語訳

- **Bearer** の日本語訳は **「持参人」** です。
- トークンの文脈では **「持参人トークン」** と訳されることが多く、「トークンを持ってきた人＝権利者」とみなす方式です。

### なぜ Bearer という名前か

- 語源は **金融の「持参人払い」**（bearer に支払う）です。
  - 小切手などで「特定の名前」を書かず、「**それを持ってきた人（bearer）に払う**」という種類の証書があります。
- トークンでも同じ考え方です。
  - **「誰のトークンか」を名前で確認するのではなく、「トークンを持ってきた人を権利者とみなす」** という方式だから「Bearer」です。
- 例え: 映画のチケット。持ってきた人が誰であれ、そのチケットを持っている人だけが入場できる。Bearer トークンも「持っていること」だけで権限が認められます（身分証確認なし）。その代わり、トークンが盗まれると第三者も使えてしまうので、保管・送信（HTTPS など）に注意が必要です。

## 4. HMAC-SHA256 の具体的なロジック

JWT の HS256 は、内部で **HMAC-SHA256** を使って「ヘッダー＋ペイロード」から署名（MAC）を計算します。

### HMAC とは

- **HMAC** = **H**ash-based **M**essage **A**uthentication **C**ode（ハッシュベースのメッセージ認証コード）。
- 「**秘密鍵**」と「**メッセージ**」を組み合わせて、**決定的な短い値（MAC）** を作る仕組みです。同じ鍵とメッセージなら常に同じ結果になり、1 ビットでもメッセージが変わると結果が変わります。

### なぜ 2 回ハッシュするか

- 鍵をそのままメッセージに繋げて 1 回だけハッシュするより、**内側・外側の 2 段階でハッシュ** することで、次のような安全性が得られます。
  - 鍵がハッシュ関数にそのまま露出しない。
  - 鍵とメッセージの混ざり方が仕様で決まっており、攻撃しにくい。

### 使うもの

- **秘密鍵（K）**: 共有秘密。HMAC-SHA256 ではブロック長に足りない場合は 0 埋め、長い場合はいったん SHA-256 でハッシュした値を使う。
- **内側パディング（ipad）**: 1 バイトの `0x36` を 64 バイト分つなげたもの（SHA-256 のブロック長 64 バイトに合わせる）。
- **外側パディング（opad）**: 1 バイトの `0x5C` を 64 バイト分つなげたもの。
- **メッセージ（M）**: JWT では「Base64URL(ヘッダー) + "." + Base64URL(ペイロード)」の文字列。

### 計算手順（自分で再現するイメージ）

1. **鍵の準備**
  - 鍵 K が 64 バイトより短い場合: 右を 0x00 で埋めて 64 バイトにする。
  - 64 バイトより長い場合: K を SHA-256 でハッシュし、その結果を 32 バイト→64 バイトになるよう 0 で埋める（仕様では「左に 0 を詰めて 64 バイト」などと定義される）。
2. **内側のハッシュ**
  - `inner = (K ⊕ ipad) || M`
  - つまり「鍵と ipad を 1 バイトずつ XOR した 64 バイト」の後ろに、メッセージ M をそのまま繋げる。
  - この `inner` を **SHA-256** でハッシュする。→ 32 バイトの値（内側ハッシュ）。
3. **外側のハッシュ（これが HMAC の結果）**
  - `outer = (K ⊕ opad) || (内側ハッシュの 32 バイト)`
  - 「鍵と opad を 1 バイトずつ XOR した 64 バイト」の後ろに、内側ハッシュの 32 バイトを繋げる。
  - この `outer` を **SHA-256** でハッシュする。→ 32 バイトの値。これが **HMAC-SHA256 の出力**（署名の中身）。
4. **JWT での使い方**
  - この 32 バイトを Base64URL エンコードしたものが、JWT の「署名」部分（3 つ目のブロック）になる。
  - 検証時は、同じ鍵・同じメッセージ（受け取ったヘッダー＋ペイロード）で同じ計算をし、出た値とトークンに付いている署名を比較する。

### 式でまとめると

- 内側: `H((K ⊕ ipad) || M)`  … H は SHA-256
- 外側: `H((K ⊕ opad) || 内側の結果)`  … この最終結果が HMAC-SHA256 の値

（⊕ = XOR、|| = 連結）

## 5. Base64 のエンコード・デコードを自分でできるまで（IT 初心者向け）

ここでは「**4 文字**」「**3 バイト**」「**6 ビット**」が何を指すか、具体例で説明します。

### 5.1 前提: バイトとビット

- **ビット（bit）**: 0 か 1 のどちらか 1 つを入れる「箱」が 1 つ。データの最小単位。
- **バイト（byte）**: ビットが 8 個並んだもの。1 バイト = 8 ビット。
  - 2^8 = 256 通りなので、**1 バイトで 0～255 の整数 1 つ**を表せます。
- 文字は「何バイトか」で表現されます。例: 英数字は UTF-8 では多くの場合 1 文字 = 1 バイト（例: `A` = 65、`H` = 72）。

**「3 バイト」** = そんな「8 ビットの箱」が 3 個並んだもの = 24 ビット分のデータ、という意味です。

### 5.2 なぜ「4 文字」なのか（Base64 の 1 ブロック）

- Base64 は **「使ってよい文字を 64 種類に決めて、1 文字で 0～63 のどれか 1 つを表す」** 方式です。
- 0～63 を表すには **6 ビットあれば十分** です（2^6 = 64）。
- つまり **1 文字 = 6 ビット** の情報を持たせます。

**入力は 3 バイト = 24 ビット** にします。

- 24 ビットを **6 ビットずつ** に分けると、**24 ÷ 6 = 4 個** に分かれます。
- 1 個の 6 ビット → Base64 の 1 文字なので、**4 個 → 4 文字** になります。

だから「**3 バイト（24 ビット）→ 6 ビット×4 → Base64 の 4 文字**」というルールになっています。

### 5.3 「3 バイトに戻す」とは（デコードの意味）

- デコードはエンコードの逆です。
- **Base64 の 4 文字** = 6 ビットが 4 個 = 24 ビット。
- 24 ビットを **8 ビットずつ** に分けると、**24 ÷ 8 = 3 個** になります。
- 8 ビット 1 個 = 1 バイトなので、**3 個 = 3 バイト** です。

つまり「**4 文字（24 ビット）→ 8 ビット×3 → 3 バイト**」がデコードのイメージです。「3 バイトに戻す」= その 3 個の 8 ビット列を、元の 3 バイトのデータとして解釈する、という意味です。

### 5.4 Base64 の 64 種類の文字（具体例）

Base64 では次の **64 種類** の文字だけを使います（RFC などで決まっています）。

- **0～25**: `A`～`Z`（26 文字）
- **26～51**: `a`～`z`（26 文字）
- **52～61**: `0`～`9`（10 文字）
- **62**: `+`
- **63**: `/`

さらに **パディング** として `=` を使います。これは「6 ビットの情報」ではなく、「ここまでで 1 ブロック（4 文字）にした」という印で、デコード時に「何文字分を無視するか」を決めるために使います。

例（番号と文字の対応）:

- 0 → `A`、1 → `B`、…、25 → `Z`
- 26 → `a`、…、51 → `z`
- 52 → `0`、…、61 → `9`
- 62 → `+`、63 → `/`

「4 文字」は、それぞれ 0～63 のどれか 1 つを表し、並べると 6+6+6+6 = 24 ビットになります。

### 5.5 具体例: 1 文字 "A" を Base64 エンコードする

- 文字 `A`（UTF-8）= **1 バイト**。中身は数字の **65**（2 進数で `01000001`）。
- Base64 は **3 バイトを 4 文字** にします。今は 1 バイトしかないので、**残り 2 バイトは 0 として扱う**（パディング）と、3 バイト = 24 ビットになります。
  - 65 の 8 ビット + 0 の 8 ビット + 0 の 8 ビット
  - 2 進: `01000001 00000000 00000000`
- これを **6 ビットずつ** に分けます:
  - `010000` → 16
  - `010000` → 16
  - `000000` → 0
  - `000000` → 0
- 変換表: 16→`Q`、16→`Q`、0→`A`、0→`A` → **QQAA**。元データは 1 バイトだけなので、出力は **2 文字＋パディング `==`** とする決まりです。つまり **QQ==** になります。

（実装によっては「0 パディング」の取り方で最後が少し変わる場合がありますが、多くの環境で `echo -n "A" | base64` は `QQ==` を出力します。）

### 5.6 具体例: "Hello" のエンコード（イメージ）

- `H`=72, `e`=101, `l`=108, `l`=108, `o`=111。5 バイト。
- 5 バイトは 3 の倍数ではないので、**最初の 3 バイト**（72, 101, 108）で 4 文字、**次の 2 バイト**（108, 111）+ 0 パディングで 3 バイト扱い→もう 4 文字。2 バイト分しかないので最後は `=` 1 個。
- 結果として「4 文字 + 4 文字」で、よく見る **SGVsbG8=** のような形になります（最後の `=` は「このブロックは 3 バイトに満たない」という印）。

### 5.7 デコードの手順（4 文字 → 3 バイト）

1. Base64 の **4 文字** を用意する（例: `SGVs`）。
2. 各文字を **0～63 の数** に戻す（`S`→18, `G`→6, `V`→21, `s`→44 など）。
3. それぞれ **6 ビット** なので、4 文字で 24 ビット。これを **上から 8 ビットずつ** 3 個に分ける。
4. 8 ビットずつ = 1 バイトずつなので、**3 バイト** が得られる。これを元データ（文字列なら UTF-8 など）として解釈する。

「4 文字を 3 バイトに戻す」= この 24 ビット→8+8+8 ビットに分けて 3 バイトとして読む、という意味です。

### 5.8 自分で試すコマンド

```bash
# エンコード（シークレット不要）
echo -n "A" | base64      # → QQ==
echo -n "Hello" | base64  # → SGVsbG8=

# デコード
echo "QQ==" | base64 -d      # → A
echo "SGVsbG8=" | base64 -d  # → Hello
```

```javascript
// Node.js
Buffer.from('A', 'utf8').toString('base64');       // "QQ=="
Buffer.from('Hello', 'utf8').toString('base64');    // "SGVsbG8="
Buffer.from('SGVsbG8=', 'base64').toString('utf8'); // "Hello"
```

JWT では同じ考え方で **Base64URL**（`+`→`-`、`/`→`_`、`=` 省略あり）を使います。エンコード・デコードにシークレットは不要で、誰でも同じ手順で変換できます。シークレットが必要なのは **署名（HMAC など）** を計算する部分だけです。
